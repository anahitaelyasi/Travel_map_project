# مستندات APIهای پروژه نیمراه (Nimrah)

## ۱. مقدمه

این سند، فهرست پیشنهادی APIهای بک‌اند نیمراه را بر اساس معماری
پنج‌میکروسرویسی مشخص می‌کند. APIها برای ارتباط فرانت‌اند با بک‌اند و ارتباط
کنترل‌شده بین سرویس‌ها استفاده می‌شوند.

پیشوند عمومی APIها:

`/api/v1`

درخواست‌های فرانت‌اند از طریق API Gateway به میکروسرویس مالک هر قابلیت
هدایت می‌شوند.


## ۲. تقسیم‌بندی میکروسرویس‌ها

  -----------------------------------------------------------------------
  میکروسرویس                          مسئولیت
  ----------------------------------- -----------------------------------
  User Service                        حساب کاربری، احراز هویت، پروفایل،
                                      مسدودسازی، گزارش‌ها و اعلان‌ها

  Travel Service                      برنامه‌های سفر، مسیرهای جایگزین و
                                      جستجوی همسفر

  Group Service                       ایجاد و مدیریت گروه‌ها، اعضا،
                                      درخواست‌های عضویت و ادغام گروه‌ها

  Communication Service               پیام‌های گروه، فایل‌ها، تصاویر،
                                      نظرسنجی‌ها و رأی‌ها

  Places Service                      مکان‌ها، ایستگاه‌ها، تصاویر مکان‌ها و
                                      مکان‌های ذخیره‌شده
  -----------------------------------------------------------------------

------------------------------------------------------------------------

# ۳. User Service APIs

مسئول مدیریت کاربران، احراز هویت، پروفایل، مسدودسازی، گزارش‌ها و اعلان‌ها.

### ۳.۱. احراز هویت

  متد    Endpoint           کاربرد
  ------ ------------------ -------------------------------------------
  POST   `/auth/register`   ثبت‌نام کاربر جدید
  POST   `/auth/login`      ورود کاربر
  POST   `/auth/refresh`    دریافت Access Token جدید با Refresh Token
  POST   `/auth/logout`     خروج کاربر و لغو نشست یا توکن مربوطه

### ۳.۲. پروفایل کاربران

  ---------------------------------------------------------------------------
  متد                     Endpoint                    کاربرد
  ----------------------- --------------------------- -----------------------
  GET                     `/users/me`                 دریافت اطلاعات کاربر
                                                      واردشده

  PATCH                   `/users/me`                 ویرایش پروفایل

  DELETE                  `/users/me`                 درخواست حذف حساب

  GET                     `/users/{user_id}/public`   دریافت اطلاعات عمومی و
                                                      مجاز یک کاربر
  ---------------------------------------------------------------------------

### ۳.۳. مسدودسازی و گزارش

  متد      Endpoint                    کاربرد
  -------- --------------------------- --------------------------------------
  POST     `/users/{user_id}/blocks`   مسدود کردن کاربر
  DELETE   `/users/{user_id}/blocks`   رفع مسدودسازی
  POST     `/reports`                  ثبت گزارش درباره کاربر، گروه یا مکان

### ۳.۴. اعلان‌ها

  -----------------------------------------------------------------------------------------
  متد                     Endpoint                                  کاربرد
  ----------------------- ----------------------------------------- -----------------------
  GET                     `/notifications`                          دریافت اعلان‌های کاربر

  PATCH                   `/notifications/{notification_id}/read`   علامت‌گذاری یک اعلان
                                                                    به‌عنوان خوانده‌شده

  POST                    `/notifications/read-all`                 علامت‌گذاری تمام اعلان‌ها
                                                                    به‌عنوان خوانده‌شده
  -----------------------------------------------------------------------------------------

اعلان‌ها در User Service ذخیره می‌شوند. سایر سرویس‌ها می‌توانند رویدادهای
مرتبط را از طریق RabbitMQ منتشر کنند تا User Service اعلان مناسب را
ایجاد کند.

# ۴. Travel Service APIs

مسئول مدیریت برنامه‌های سفر، مسیرهای جایگزین و پیدا کردن افراد یا گروه‌های
مناسب برای همسفری.

### ۴.۱. برنامه‌های سفر

  متد     Endpoint                           کاربرد
  ------- ---------------------------------- ----------------------------
  POST    `/travel-plans`                    ایجاد برنامه سفر جدید
  GET     `/travel-plans`                    دریافت برنامه‌های سفر کاربر
  GET     `/travel-plans/{plan_id}`          دریافت جزئیات برنامه سفر
  PATCH   `/travel-plans/{plan_id}`          ویرایش برنامه سفر
  POST    `/travel-plans/{plan_id}/cancel`   لغو برنامه سفر

هر برنامه سفر می‌تواند متعلق به یک کاربر یا یک گروه باشد. مجوز ایجاد و
ویرایش آن باید بر اساس نوع مالک و شناسه مالک بررسی شود.

### ۴.۲. مسیرهای جایگزین

هر برنامه سفر می‌تواند چند مسیر جایگزین داشته باشد؛ برای مثال، کاربر
می‌تواند برای سفر ساری به تهران چند نقطه شروع و پایان متفاوت تعریف کند.

  متد      Endpoint                            کاربرد
  -------- ----------------------------------- ------------------------
  POST     `/travel-plans/{plan_id}/options`   افزودن مسیر جایگزین
  GET      `/travel-plans/{plan_id}/options`   دریافت مسیرهای جایگزین
  PATCH    `/travel-options/{option_id}`       ویرایش مسیر جایگزین
  DELETE   `/travel-options/{option_id}`       حذف مسیر جایگزین

### ۴.۳. جستجوی همسفر (Matching)

  --------------------------------------------------------------------------------------------------
  متد                     Endpoint                                           کاربرد
  ----------------------- -------------------------------------------------- -----------------------
  GET                     `/travel-plans/{plan_id}/matches`                  پیدا کردن افراد و
                                                                             گروه‌های دارای مسیر یا
                                                                             زمان مشابه

  GET                     `/travel-plans/{plan_id}/matches/{candidate_id}`   دریافت جزئیات یک گزینه
                                                                             پیشنهادی
  --------------------------------------------------------------------------------------------------

نمونه درخواست:

`GET /api/v1/travel-plans/{plan_id}/matches?limit=20&cursor={cursor}`

الگوریتم Matching می‌تواند فاصله مبدأها و مقصدها، تاریخ و ساعت حرکت،
محدوده قابل قبول کاربر، ظرفیت گروه و وضعیت فعال بودن برنامه سفر را برای
رتبه‌بندی در نظر بگیرد.

هر فرد یا گروه باید در نتایج یک برنامه سفر فقط یک بار نمایش داده شود؛
حتی اگر چند مسیر جایگزین او با مسیر جستجوکننده تطبیق داشته باشد.
برنامه‌های لغوشده، غیرفعال، غیرقابل جستجو و برنامه‌های شخصی‌ای که به عضویت
فعال یک گروه تبدیل شده‌اند، نباید به‌عنوان مسافر مستقل نمایش داده شوند.

------------------------------------------------------------------------

# ۵. Group Service APIs

مسئول ایجاد و مدیریت گروه‌ها، اعضا، درخواست‌های عضویت، جذب عضو، ادغام
گروه‌ها و انتقال مالکیت. پیام‌ها و فایل‌های چت در Communication Service
مدیریت می‌شوند.

### ۵.۱. مدیریت گروه‌ها

  -----------------------------------------------------------------------------------------
  متد                     Endpoint                                  کاربرد
  ----------------------- ----------------------------------------- -----------------------
  POST                    `/groups`                                 ایجاد گروه جدید

  GET                     `/groups/me`                              دریافت گروه‌هایی که
                                                                    کاربر عضو آن‌هاست

  GET                     `/groups/{group_id}`                      دریافت اطلاعات گروه

  PATCH                   `/groups/{group_id}`                      ویرایش اطلاعات مجاز
                                                                    گروه

  GET                     `/groups/{group_id}/members`              دریافت اعضای گروه

  POST                    `/groups/{group_id}/leave`                خروج کاربر از گروه

  DELETE                  `/groups/{group_id}/members/{user_id}`    حذف عضو توسط مالک یا
                                                                    مدیر مجاز

  POST                    `/groups/{group_id}/transfer-ownership`   انتقال مالکیت به یکی از
                                                                    اعضای فعال
  -----------------------------------------------------------------------------------------

### ۵.۲. مدیریت جذب عضو

  متد    Endpoint                                 کاربرد
  ------ ---------------------------------------- ----------------------
  POST   `/groups/{group_id}/recruitment/open`    فعال کردن جذب عضو
  POST   `/groups/{group_id}/recruitment/close`   غیرفعال کردن جذب عضو

با فعال شدن جذب عضو، Group Service وضعیت را از طریق رویداد به Travel
Service اطلاع می‌دهد تا برنامه سفر گروه برای جستجوی همسفر قابل نمایش شود.
با تکمیل ظرفیت یا بسته شدن جذب عضو، وضعیت جستجو نیز به‌روزرسانی می‌شود.

### ۵.۳. درخواست‌های عضویت

  --------------------------------------------------------------------------------------------
  متد                     Endpoint                                     کاربرد
  ----------------------- -------------------------------------------- -----------------------
  POST                    `/membership-requests`                       ارسال درخواست عضویت

  GET                     `/membership-requests`                       دریافت درخواست‌های ورودی
                                                                       یا خروجی

  GET                     `/membership-requests/{request_id}`          دریافت جزئیات درخواست

  POST                    `/membership-requests/{request_id}/accept`   پذیرش درخواست

  POST                    `/membership-requests/{request_id}/reject`   رد درخواست

  POST                    `/membership-requests/{request_id}/cancel`   لغو درخواست ارسال‌شده
  --------------------------------------------------------------------------------------------

نمونه فیلتر:

`GET /api/v1/membership-requests?direction=incoming&status=pending`

این سیستم از چهار حالت پشتیبانی می‌کند: درخواست فرد به فرد، فرد به گروه،
گروه به فرد و گروه به گروه.

در درخواست گروه به گروه، در صورت پذیرش، تمام اعضای فعال گروه مبدأ منتقل
می‌شوند؛ مشروط بر اینکه ظرفیت گروه مقصد کافی باشد. پذیرش درخواست باید با
تراکنش و قفل‌گذاری مناسب انجام شود تا پذیرش هم‌زمان باعث عضویت تکراری یا
عبور از ظرفیت نشود.

# ۶. Communication Service APIs

مسئول تمام قابلیت‌های ارتباطی گروه‌ها شامل پیام متنی، پیام سیستمی، تصاویر،
فایل‌ها، نظرسنجی‌ها و رأی‌ها.

### ۶.۱. پیام‌های گروه

  -------------------------------------------------------------------------------
  متد                     Endpoint                        کاربرد
  ----------------------- ------------------------------- -----------------------
  GET                     `/groups/{group_id}/messages`   دریافت پیام‌های گروه

  POST                    `/groups/{group_id}/messages`   ارسال پیام جدید

  WS                      `/ws/groups/{group_id}`         ارتباط WebSocket برای
                                                          پیام‌رسانی لحظه‌ای
  -------------------------------------------------------------------------------

پیام‌ها می‌توانند شامل متن، پیام سیستمی، ارجاع به فایل پیوست یا نظرسنجی
باشند. پیام‌های سیستمی برای رویدادهایی مانند ورود یا خروج عضو، تغییر
مالک، شروع یا پایان جذب عضو و ادغام گروه ثبت می‌شوند.

Communication Service باید پیش از نمایش یا ارسال پیام، عضویت و مجوز
دسترسی کاربر را از طریق Group Service یا یک نمای داده‌ای همگام‌سازی‌شده و
معتبر بررسی کند. این سرویس نباید مستقیماً به پایگاه داده Group Service
دسترسی داشته باشد.

### ۶.۲. فایل‌ها و تصاویر

  ---------------------------------------------------------------------------------------------
  متد                     Endpoint                                      کاربرد
  ----------------------- --------------------------------------------- -----------------------
  POST                    `/groups/{group_id}/attachments/upload-url`   دریافت آدرس موقت و مجاز
                                                                        برای بارگذاری فایل یا
                                                                        تصویر

  POST                    `/groups/{group_id}/attachments/confirm`      تأیید بارگذاری و ثبت
                                                                        اطلاعات فایل
  ---------------------------------------------------------------------------------------------

فایل واقعی در فضای ذخیره‌سازی مانند MinIO یا S3 نگهداری می‌شود. اطلاعاتی
مانند نام، نوع، حجم و کلید ذخیره‌سازی در جدول MESSAGE_ATTACHMENTS قرار
می‌گیرد.

### ۶.۳. نظرسنجی‌های گروه

  --------------------------------------------------------------------------------------------
  متد                     Endpoint                                     کاربرد
  ----------------------- -------------------------------------------- -----------------------
  POST                    `/groups/{group_id}/polls`                   ایجاد نظرسنجی جدید

  GET                     `/groups/{group_id}/polls/{poll_id}`         دریافت اطلاعات و نتایج
                                                                       نظرسنجی

  POST                    `/groups/{group_id}/polls/{poll_id}/votes`   ثبت رأی کاربر

  POST                    `/groups/{group_id}/polls/{poll_id}/close`   بستن نظرسنجی
  --------------------------------------------------------------------------------------------

هر نظرسنجی شامل پرسش، گزینه‌ها، تنظیمات رأی‌دهی، زمان پایان و وضعیت فعال
یا بسته است.

قوانین رأی‌دهی: - فقط اعضای مجاز گروه می‌توانند رأی دهند. - در نظرسنجی
تک‌انتخابی، هر کاربر فقط یک گزینه را انتخاب می‌کند. - در نظرسنجی
چندانتخابی، کاربر می‌تواند چند گزینه را انتخاب کند. - ثبت رأی تکراری برای
یک گزینه مجاز نیست. - پس از بسته شدن نظرسنجی، رأی جدید پذیرفته نمی‌شود.

ایجاد پیام نظرسنجی و اطلاعات مربوط به آن باید به‌صورت هماهنگ و با تراکنش
پایگاه داده انجام شود.

# ۷. Places Service APIs

مسئول مدیریت مکان‌ها، ایستگاه‌ها و اطلاعات نمایش‌داده‌شده روی نقشه.

### ۷.۱. مدیریت مکان‌ها

  متد     Endpoint               کاربرد
  ------- ---------------------- -------------------------------------
  GET     `/places`              دریافت مکان‌های تأییدشده
  GET     `/places/{place_id}`   دریافت جزئیات مکان
  POST    `/places`              ثبت مکان جدید توسط کاربر
  PATCH   `/places/{place_id}`   ویرایش اطلاعات مکان توسط کاربر مجاز

نمونه درخواست:

`GET /api/v1/places?category=station&city=Tehran`

دسته‌بندی مکان‌ها می‌تواند شامل ایستگاه، رستوران، هتل، جاذبه گردشگری و سایر
مکان‌های عمومی باشد. ایستگاه‌ها و سایر مکان‌ها در جدول مشترک PLACES ذخیره
می‌شوند و نوع آن‌ها با فیلد category مشخص می‌شود.

### ۷.۲. تصاویر مکان‌ها

  ----------------------------------------------------------------------------------------
  متد                     Endpoint                                 کاربرد
  ----------------------- ---------------------------------------- -----------------------
  POST                    `/places/{place_id}/images/upload-url`   دریافت آدرس موقت
                                                                   بارگذاری تصویر

  POST                    `/places/{place_id}/images/confirm`      تأیید بارگذاری و ثبت
                                                                   اطلاعات تصویر
  ----------------------------------------------------------------------------------------

### ۷.۳. درخواست مالکیت مکان

  ----------------------------------------------------------------------------
  متد                     Endpoint                     کاربرد
  ----------------------- ---------------------------- -----------------------
  POST                    `/places/{place_id}/claim`   ثبت درخواست مالکیت یا
                                                       مدیریت مکان

  ----------------------------------------------------------------------------

### ۷.۴. مکان‌های ذخیره‌شده

  متد      Endpoint                    کاربرد
  -------- --------------------------- ------------------------------
  POST     `/places/{place_id}/save`   ذخیره مکان در فهرست کاربر
  DELETE   `/places/{place_id}/save`   حذف مکان از فهرست ذخیره‌شده‌ها

# ۸. Admin APIs

پنل مدیریت از APIهای مدیریتی سرویس‌های مالک داده استفاده می‌کند. دسترسی به
این APIها فقط برای کاربران دارای نقش و مجوز مدیریتی مجاز است.

  --------------------------------------------------------------------------------------------
  متد               Endpoint                               سرویس مالک        کاربرد
  ----------------- -------------------------------------- ----------------- -----------------
  GET               `/admin/users`                         User              دریافت فهرست
                                                                             کاربران

  PATCH             `/admin/users/{user_id}/status`        User              مسدودسازی یا
                                                                             فعال‌سازی حساب

  GET               `/admin/groups`                        Group             دریافت فهرست
                                                                             گروه‌ها

  PATCH             `/admin/groups/{group_id}/status`      Group             تغییر وضعیت گروه

  GET               `/admin/places`                        Places            مشاهده مکان‌های
                                                                             ثبت‌شده

  POST              `/admin/places/{place_id}/approve`     Places            تأیید مکان

  POST              `/admin/places/{place_id}/reject`      Places            رد مکان

  GET               `/admin/reports`                       User              مشاهده گزارش‌ها

  POST              `/admin/reports/{report_id}/resolve`   User              رسیدگی به گزارش
  --------------------------------------------------------------------------------------------

هر سرویس باید مجوز مدیر را در سمت بک‌اند بررسی کند. مخفی کردن دکمه‌ها در
فرانت‌اند به‌تنهایی کنترل دسترسی محسوب نمی‌شود.

# ۹. ارتباط بین میکروسرویس‌ها

ارتباط بین میکروسرویس‌ها از دو روش اصلی انجام می‌شود.

### ۹.۱. ارتباط هم‌زمان با REST API

برای عملیاتی استفاده می‌شود که سرویس درخواست‌کننده به پاسخ مستقیم نیاز
دارد؛ مانند بررسی اعتبار کاربر، دریافت وضعیت عضویت یا ایجاد برنامه سفر
گروه.

### ۹.۲. ارتباط غیرهم‌زمان با RabbitMQ

برای اطلاع‌رسانی رویدادها و هماهنگ نگه داشتن سرویس‌ها از RabbitMQ استفاده
می‌شود.

  رویداد               منتشرکننده       مصرف‌کنندگان پیشنهادی
  -------------------- ---------------- --------------------------------
  UserCreated          User Service     سرویس‌های نیازمند اطلاعات کاربر
  UserBlocked          User Service     Travel و Group
  TravelPlanCreated    Travel Service   Group، در صورت نیاز
  TravelPlanUpdated    Travel Service   Group
  GroupCreated         Group Service    Travel و Communication
  MemberJoined         Group Service    Travel، Communication و User
  MemberLeft           Group Service    Travel، Communication و User
  OwnerChanged         Group Service    Communication و User
  RecruitmentChanged   Group Service    Travel و Communication
  GroupMerged          Group Service    Travel، Communication و User
  GroupDissolved       Group Service    Travel و Communication
  PlaceApproved        Places Service   سرویس‌های نیازمند اطلاعات مکان

برای جلوگیری از گم شدن رویدادها، استفاده از الگوی Transactional Outbox
پیشنهاد می‌شود. مصرف‌کنندگان نیز باید در برابر دریافت چندباره یک رویداد
مقاوم باشند.

------------------------------------------------------------------------

# ۱۰. امنیت و استانداردهای API

موارد زیر باید در پیاده‌سازی رعایت شوند:

۱. استفاده از JWT برای احراز هویت؛\
۲. استفاده از Role-Based Access Control برای تعیین سطح دسترسی؛\
۳. بررسی مالکیت منابع و مجوز کاربر در سمت بک‌اند؛\
۴. اعتبارسنجی ورودی‌ها و خروجی‌ها با Pydantic؛\
۵. استفاده از HTTPS؛\
۶. محدود کردن تعداد درخواست‌ها در صورت نیاز؛\
۷. محدود کردن نوع و حجم فایل‌های ارسالی؛\
۸. استفاده از آدرس‌های موقت و مجاز برای بارگذاری و دریافت فایل‌ها؛\
۹. استفاده از Pagination برای فهرست‌های طولانی؛\
۱۰. استفاده از تراکنش و قفل‌گذاری برای عملیات حساس؛\
۱۱. جلوگیری از دسترسی مستقیم یک میکروسرویس به پایگاه داده سرویس دیگر؛\
۱۲. محافظت از APIهای داخلی در برابر دسترسی عمومی.

------------------------------------------------------------------------

# ۱۱. قالب استاندارد پاسخ API

پاسخ APIها در قالب JSON ارائه می‌شود.

### نمونه پاسخ موفق

``` json
{
  "success": true,
  "data": {
    "id": "GROUP_UUID",
    "name": "گروه سفر تهران"
  },
  "message": "عملیات با موفقیت انجام شد."
}
```

### نمونه پاسخ خطا

``` json
{
  "success": false,
  "error": {
    "code": "GROUP_CAPACITY_REACHED",
    "message": "ظرفیت گروه تکمیل شده است."
  }
}
```

### کدهای وضعیت HTTP

  کد    مفهوم
  ----- --------------------------------------------------
  200   درخواست با موفقیت انجام شد
  201   موجودیت جدید ایجاد شد
  204   عملیات موفق بود و محتوایی برای بازگشت وجود ندارد
  400   درخواست نامعتبر است
  401   کاربر احراز هویت نشده است
  403   کاربر مجوز دسترسی ندارد
  404   منبع موردنظر پیدا نشد
  409   تعارض در وضعیت یا اطلاعات وجود دارد
  422   اطلاعات ورودی از نظر اعتبارسنجی قابل قبول نیست
  429   تعداد درخواست‌ها بیش از حد مجاز است
  500   خطای داخلی سرور

# ۱۳. مستندات تعاملی API

برای مشاهده جزئیات فنی APIها، شامل پارامترها، مدل درخواست و پاسخ و امکان
ارسال درخواست آزمایشی، از مستندات خودکار OpenAPI/Swagger هر میکروسرویس
استفاده می‌شود.

FastAPI امکان تولید خودکار این مستندات را فراهم می‌کند. آدرس Swagger هر
سرویس می‌تواند در محیط توسعه به‌صورت جداگانه در دسترس باشد یا از طریق API
Gateway مسیریابی شود.
